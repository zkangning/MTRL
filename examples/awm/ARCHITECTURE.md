## Overview

The AWM integration enables RLLM to train agents on diverse virtual environments generated by the AWM framework. Each environment is a self-contained FastAPI application with:

- SQLite database with realistic schema and data
- Business logic APIs
- MCP (Model Context Protocol) server for tool-based interaction
- Automated verification system for reward computation

## Component Details

### 1. AWMEnvironment (`rllm/environments/awm/awm_env.py`)

#### Responsibilities

- **Server Lifecycle Management**: Start/stop MCP servers for each episode
- **Database Management**: Create temporary copies of scenario databases
- **Tool Execution**: Route agent actions to MCP server tool calls
- **State Tracking**: Maintain episode history and step counter

#### Key Methods

```python
class AWMEnvironment(BaseEnv):
    def reset(self) -> Tuple[Observation, Info]:
        """Start new episode: launch MCP server, init database"""
        
    def step(self, action: str) -> Tuple[Observation, Reward, Done, Info]:
        """Execute one step: parse tool calls, execute, return results"""
        
    def _start_server(self) -> None:
        """Internal: Launch FastAPI/MCP server process"""
        
    def _cleanup_server(self) -> None:
        """Internal: Terminate server and clean up temp files"""
```

#### Configuration

```python
env = AWMEnvironment(
    scenario_name="e_commerce",           # Scenario identifier
    task_description="Find a laptop...",  # User task
    env_code="...",                       # FastAPI code from gen_envs.jsonl
    db_path="...",                        # Path to SQLite database
    verifier_code="...",                  # Verification code
    max_steps=30,                         # Max interaction steps
    server_start_timeout=30.0,            # Server startup timeout
)
```

### 2. Reward Functions (`rllm/environments/awm/awm_reward.py`)

#### AWMMCPPureCodeRewardFn

Uses verification code that returns binary results:

```python
result = verify(initial_db_path, final_db_path, final_answer)
# Returns: {"result": "complete"} or {"result": "others"}
```

**Pros**:
- Fast execution (no LLM calls)
- Deterministic results
- Lower computational cost

**Cons**:
- Less nuanced judgment
- May miss partial completions

#### AWMMCPRewardFn

Uses verification code that returns info dict for LLM judgment:

```python
info = verify(initial_db_path, final_db_path)
# Returns: {"items_found": 3, "required_items": 5, ...}

# LLM judges based on info
judgment = llm_judge(task, final_answer, info)
# Returns: {"completed": true/false, "confidence": 0.9}
```

**Pros**:
- More nuanced evaluation
- Can handle partial credit
- Adaptable to complex tasks

**Cons**:
- Requires LLM calls (slower)
- Higher computational cost

### 3. Data Loading (`rllm/data/utils.py`)

#### load_awm_dataset

```python
def load_awm_dataset(
    dataset_path: str = "Snowflake/AgenticWorldModel",
    split: str = "train",
    num_scenarios: int = 0,
    tasks_per_scenario: int = 10,
    verification_mode: str = "pure_code"
) -> List[Dict]:
    """Load and preprocess AWM data from HuggingFace"""
```

**Data Processing Pipeline**:

1. Load all JSONL files from HuggingFace
2. Build lookup dictionaries for scenarios, tasks, databases
3. Filter by scenario and task count
4. Create standardized samples with `create_standard_sample()`
5. Shuffle with fixed seed for reproducibility

**Data Format**:

```python
{
    "prompt": "<task_description>",
    "response": "",
    "task_type": "awm",
    "data_source": "awm",
    "extra_info": json.dumps({
        "scenario": "scenario_name",
        "task": "task_description",
        "env_code": "...",           # FastAPI code
        "db_schema": {...},          # Database schema
        "db_sample": {...},          # Sample data
        "verifier_code": "...",      # Verification code
        "max_steps": 30,
    })
}
```

## Data Flow

### Episode Initialization

```
1. Trainer calls env.reset()
   │
   ├──► Load scenario data from task
   │
   ├──► Create temp directory
   │    └── Copy database file
   │
   ├──► Modify environment code
   │    └── Replace db_path, set port
   │
   ├──► Start MCP server subprocess
   │    └── python temp_server.py
   │
   ├──► Wait for server ready
   │    └── Health check on port
   │
   └──► Initialize MCP connection
        └── Fetch available tools
```

### Step Execution

```
2. Trainer calls env.step(action)
   │
   ├──► Parse action for tool calls
   │    └── Extract <tool_call> tags
   │
   ├──► Execute tool calls via MCP
   │    ├── list_tools: Return formatted tool list
   │    └── call_tool: Forward to MCP server
   │
   ├──► Format results as observation
   │
   └──► Check termination conditions
        ├── max_steps reached?
        └── no tool calls (final answer)?
```

### Reward Computation

```
3. On episode termination
   │
   ├──► Execute verification code
   │    ├── Setup: Make DB read-only
   │    ├── Execute: Run verify() function
   │    └── Cleanup: Restore DB permissions
   │
   ├──► Parse verification result
   │    ├── pure_code: Check "complete"/"others"
   │    └── sql: Use LLM to judge info dict
   │
   └──► Return RewardOutput
        └── reward: 1.0 or 0.0
```

### Cleanup

```
4. env.close() or episode end
   │
   ├──► Terminate MCP server
   │    └── SIGTERM → SIGKILL if needed
   │
   ├──► Remove temp directory
   │    └── Database + server code
   │
   └──► Reset internal state
```

class AWMEnvironment(BaseEnv):

## Design Decisions

### 1. Why Separate MCP Server Per Episode?

**Decision**: Each episode starts a fresh MCP server with a copy of the database.

**Rationale**:
- **Isolation**: Prevents state pollution between episodes
- **Reproducibility**: Each episode starts from known initial state
- **Parallel Safety**: Multiple episodes can run concurrently without conflicts

**Trade-off**: Server startup overhead (~3-5 seconds per episode)

**Mitigation**:
- Limit parallel workers to control server count
- Future: Implement server pooling for reuse

### 2. Why Pure Code Verification by Default?

**Decision**: Default to `AWMMCPPureCodeRewardFn` over `AWMMCPRewardFn`

**Rationale**:
- **Speed**: No LLM calls needed for reward computation
- **Cost**: Lower API/compute costs during training
- **Determinism**: Reproducible results

**When to use LLM-augmented verification**:
- Complex tasks with partial credit
- When verification logic is hard to encode
- Evaluation/testing scenarios

### 3. Why Tool-Based Interaction?

**Decision**: Use MCP tool protocol instead of direct API calls

**Rationale**:
- **Standardization**: MCP is becoming industry standard
- **Discoverability**: Agents can list and understand available tools
- **Flexibility**: Easy to add/modify environment capabilities
- **Observability**: Clear action/reward structure for RL

### 4. Why Temporary Databases?

**Decision**: Copy database to temp directory for each episode

**Rationale**:
- **Write Safety**: Agent can modify database without affecting source
- **Parallel Safety**: Each episode has isolated database
- **Cleanup**: Automatic cleanup on episode end

**Implementation**:
```python
temp_dir = tempfile.mkdtemp()
shutil.copy2(db_path, os.path.join(temp_dir, "environment.db"))
# Use temp database for this episode
```

### 5. Why Hydra Configuration?

**Decision**: Use Hydra for configuration management

**Rationale**:
- **Composability**: Easy to override specific parameters
- **Reproducibility**: Configs are versioned and shareable
- **Flexibility**: Command-line overrides for experimentation

**Usage**:
```bash
# Default config
python train_awm.py

# Override specific values
python train_awm.py data.train_scenarios=200 rllm.agent.max_steps=40
```

## Future Improvements

1. **Server Pooling**: Maintain pool of pre-started servers to reduce startup overhead
2. **Incremental Verification**: Provide intermediate rewards during episode
3. **Multi-Scenario Training**: Train on multiple scenarios simultaneously
4. **Curriculum Learning**: Progressively increase scenario difficulty
5. **Offline RL**: Support training from logged AWM episodes
